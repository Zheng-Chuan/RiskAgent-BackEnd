# Phase 14: 性能验证与 LLM 成本模型

## 状态

规划中

## 背景

Phase 10 的 5 分钟主动监控全链路验证已于 2026-08-03 完成. 验证过程中收集到以下性能数据点:

- LLM 调用次数：133 次 / 5 分钟（deepseek/deepseek-chat）
- LLM 调用频率：约 26.6 次/分钟
- 监控循环间隔：SystemEngineer 30s, RiskAnalyst 45s, Orchestrator 60s, Critic 90s, Intent 120s
- 每轮监控循环可能触发：意图识别（1 次 LLM）+ 编排规划（1 次 LLM）+ 评审（1 次 LLM）+ ReAct 循环（3-5 次 LLM）
- Trace 记录：15 个 entry / 每次完整链路

当前缺乏以下关键能力：

1. **系统压测数据**：最大并发、吞吐量、延迟分布均未知，无法回答「系统能扛住几个并发故障」
2. **LLM 调用成本模型**：每次调用 token 消耗未量化，OpenRouter 定价未纳入计算，日/月成本估算缺失
3. **长时间运行的资源消耗趋势**：内存、Redis 连接、MySQL 连接在持续运行下的增长曲线未知
4. **故障恢复时间指标**：MTTR（Mean Time To Recovery）未定义和测量

> **Phase 10 验证暴露的可靠性问题**：信念累积（同一 Redis 异常在 10 轮感知循环中被重复处理）、LLM 调用频率线性增长（不做去重时 133 次/5min → ~38304 次/天）、成本模型缺失（无法量化主动监控的运行成本）. 详见 [RFC-006](../decisions/RFC-006-bdi-belief-dedup-intention-idempotency.md) 的 Phase 10 验证发现.

## 核心目标

1. 建立 LLM 调用成本模型，量化主动监控的运行成本
2. 执行系统压测，验证在多故障并发场景下的系统稳定性
3. 定义性能基线（SLO）和成本预算
4. 为生产部署提供容量规划和成本预估依据

## 时间盒与资源

- 时间: 3 周
- 优先级: 高
- 依赖: Phase 10 已完成 ✅, RFC-006 BDI 去重需先行完成

## 工作范围

### In Scope

- LLM 调用成本模型：量化每次 LLM 调用的 token 消耗（prompt tokens + completion tokens），建立成本预估表
- 系统压测：单故障、多故障并发、高频故障、长时间运行四类场景
- SLO 定义：故障检测延迟、处置完成延迟、Trace 完整性、LLM 成本四项基线
- LLM 调用预算上限与熔断阈值定义，与 Phase 10 的 ProactiveBudget 治理集成
- 容量规划：基于压测数据推算生产部署所需资源配额

### Out of Scope

- 前端性能监控仪表盘：归属前端项目，本期仅保证后端数据可被消费
- LLM 模型选型优化：本期不更换模型，仅在当前 deepseek/deepseek-chat 基线上量化成本
- 分布式压测框架搭建：本期使用单机并发模拟，不引入 k6 / Locust 等外部框架
- 多集群容量规划：本期仅覆盖单 K8s 集群部署

## 详细 Checkpoint

### 方向二十. LLM 成本模型

#### 目标

量化主动监控的 LLM 调用成本，建立可预测的成本预估模型和预算熔断机制.

- [ ] Checkpoint 20.1.1 Token 消耗量化
  - 实现项: 在 LLM 调用链路中采集每次调用的 prompt tokens + completion tokens，按 Agent 角色和调用阶段分类统计
  - 验收方法: 运行一次完整监控链路，检查 token 统计记录与 OpenRouter API 返回值一致
  - 验收证据: token 消耗明细表（按 Agent × 阶段维度）
  - 通过标准: 每次调用均有 token 消耗记录，统计值与 API 返回值偏差 < 1%

- [ ] Checkpoint 20.1.2 单次链路成本计算
  - 实现项: 基于 OpenRouter 定价计算单次完整监控链路的平均 LLM 成本（意图识别 + 编排规划 + 评审 + ReAct 循环）
  - 验收方法: 对比 5 次完整链路的实际成本与计算模型预估值
  - 验收证据: 成本计算模型 + 5 次实测对照表
  - 通过标准: 模型预估值与实际成本偏差 < 10%

- [ ] Checkpoint 20.1.3 成本预估表
  - 实现项: 建立 5min / 1h / 24h / 7d 四个时间窗口的成本预估表，区分「有信念去重」和「无信念去重」两种场景
  - 验收方法: 对照 Phase 10 的 133 次/5min 实测数据验证 5min 预估准确性
  - 验收证据: 成本预估表（4 时间窗口 × 2 场景）
  - 通过标准: 5min 预估值与 Phase 10 实测值偏差 < 15%；去重场景成本降低 > 80%

- [ ] Checkpoint 20.1.4 预算上限与熔断阈值
  - 实现项: 定义 LLM 调用预算上限（5min / 1h / 24h 三级），超限触发熔断降级为纯规则处置
  - 验收方法: 注入高频异常信号触发预算超限，观察熔断行为
  - 验收证据: 预算配置文件 + 熔断触发 trace
  - 通过标准: 超限后 30s 内触发熔断；熔断后不产生 LLM 调用；与 ProactiveBudget 集成无旁路

### 方向二十一. 系统压测

#### 目标

验证主动监控系统在多故障并发和长时间运行场景下的稳定性，暴露瓶颈和资源泄漏.

- [ ] Checkpoint 20.2.1 单故障端到端延迟
  - 实现项: 注入 1 个故障（Redis 中断），测量检测 → 告警 → 处置 → 恢复的端到端延迟
  - 验收方法: 从注入故障到 Trace status=completed 的时间差
  - 验收证据: 端到端延迟 trace + 各阶段耗时分解
  - 通过标准: 端到端延迟 < 60s（检测 < 30s + 处置 < 30s）

- [ ] Checkpoint 20.2.2 多故障并发场景
  - 实现项: 同时注入 2-3 个故障（如 Redis 中断 + MySQL 慢查询 + 容器 exited），验证系统不崩溃
  - 验收方法: 观察 5 分钟内所有故障均被检测和处置，无协程退出或资源耗尽
  - 验收证据: 多故障并发 trace + 资源监控快照
  - 通过标准: 3 个并发故障全部完成处置；系统无崩溃；Trace 完整性 100%

- [ ] Checkpoint 20.2.3 高频故障场景（信念去重验证）
  - 实现项: 每 30 秒注入新故障，持续 5 分钟，验证 RFC-006 信念去重效果（同一信号不重复处理）
  - 验收方法: 对比「RFC-006 未实现」和「RFC-006 已实现」两种状态下的 LLM 调用次数
  - 验收证据: 去重前后 LLM 调用次数对照表 + 信念处理 trace
  - 通过标准: 去重后 LLM 调用次数降低 > 80%；首次告警投递时机不受影响

- [ ] Checkpoint 20.2.4 长时间运行资源消耗
  - 实现项: 持续运行 1 小时，每 60s 采集内存占用、Redis 连接数、MySQL 连接数、协程数量
  - 验收方法: 绘制资源消耗趋势图，检查是否有内存泄漏或连接泄漏
  - 验收证据: 1 小时资源消耗时序数据 + 趋势图
  - 通过标准: 内存增长 < 20%（非泄漏）；Redis/MySQL 连接数稳定不增长；无协程泄漏

### 方向二十二. SLO 定义

#### 目标

定义可量化的性能基线，作为生产部署的准入标准.

- [ ] Checkpoint 20.3.1 故障检测延迟 SLO
  - 实现项: 定义故障检测延迟 SLO，目标 < 60s（从故障注入到感知层检测到异常信号的时间）
  - 验收方法: 对 10 个不同类型故障测量检测延迟，取 P95
  - 验收证据: 10 次检测延迟记录 + P95 统计
  - 通过标准: P95 检测延迟 < 60s

- [ ] Checkpoint 20.3.2 处置完成延迟 SLO
  - 实现项: 定义处置完成延迟 SLO，目标 < 300s（从故障检测到 Trace status=completed 的时间）
  - 验收方法: 对 10 个不同类型故障测量处置延迟，取 P95
  - 验收证据: 10 次处置延迟记录 + P95 统计
  - 通过标准: P95 处置延迟 < 300s

- [ ] Checkpoint 20.3.3 Trace 完整性 SLO
  - 实现项: 定义 Trace 完整性 SLO，目标 100%（每次完整链路在 run_trace.v2 中有完整 entry）
  - 验收方法: 对压测期间所有 trace 检查 entry 完整性（感知 → 告警 → 意图 → 编排 → 评审 → 执行 → 收据）
  - 验收证据: trace 完整性审查报告
  - 通过标准: Trace 完整性 = 100%

- [ ] Checkpoint 20.3.4 LLM 成本 SLO
  - 实现项: 定义 LLM 成本 SLO，目标 5min 内 LLM 调用成本 < $X（X 基于成本模型确定）
  - 验收方法: 压测期间统计 5min 窗口 LLM 调用成本
  - 验收证据: 5min 成本统计报告
  - 通过标准: 5min 成本 < 预算上限；去重后成本较未去重降低 > 80%

## 风险与缓解

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| 压测消耗大量 LLM token | 成本超支 | 压测使用 ProactiveBudget 预算隔离；高频场景使用 fallback 模拟模式 |
| 长时间运行暴露隐蔽资源泄漏 | 测试环境不稳定 | 1 小时运行前先做 5min 基线采集；发现泄漏立即终止并记录 |
| 信念去重未实现导致压测数据失真 | 高频故障场景 LLM 调用爆炸 | RFC-006 必须先于 P1 压测完成；P1 依赖 RFC-006 |
| SLO 目标过于激进 | 验收无法通过 | SLO 基于 Phase 10 实测数据设定，预留缓冲 |

## 实施计划

| 阶段 | 内容 | 依赖 | 预计工时 |
|------|------|------|---------|
| P0 | LLM 成本模型（Checkpoint 20.1.x） | Phase 10 完成 ✅ | 1 周 |
| P1 | 系统压测（Checkpoint 20.2.x） | RFC-006 BDI 去重完成 | 1.5 周 |
| P2 | SLO 定义（Checkpoint 20.3.x） | P0 + P1 | 0.5 周 |

核心原则：先量化成本（P0），再压测验证（P1），最后定义基线（P2）. P0 不依赖 RFC-006，可并行启动.

## 分阶段中间验收标准

### P0 验收: LLM 成本模型

| 验收项 | 方法 | 通过标准 | 证据类型 |
|--------|------|---------|---------|
| Token 消耗量化 | 运行完整链路检查 token 记录 | 每次调用有 token 记录，偏差 < 1% | token 明细表 |
| 单次链路成本 | 5 次实测 vs 模型预估 | 偏差 < 10% | 成本对照表 |
| 成本预估表 | 对照 Phase 10 实测 | 5min 偏差 < 15% | 预估表 |
| 预算熔断 | 注入高频信号触发超限 | 30s 内触发熔断 | 熔断 trace |

关键中间结果: 成本预估表 + 预算熔断配置 是 P1 压测的前置条件.

### P1 验收: 系统压测

| 验收项 | 方法 | 通过标准 | 证据类型 |
|--------|------|---------|---------|
| 单故障延迟 | 注入 1 个故障测端到端 | < 60s | 延迟 trace |
| 多故障并发 | 同时注入 3 个故障 | 全部处置完成无崩溃 | 并发 trace |
| 信念去重效果 | 30s/次高频注入，对比去重前后 | LLM 调用降低 > 80% | 对照表 |
| 长时间运行 | 持续 1 小时采集资源 | 内存增长 < 20%，连接稳定 | 资源趋势图 |

### P2 验收: SLO 定义

| 验收项 | 方法 | 通过标准 | 证据类型 |
|--------|------|---------|---------|
| 检测延迟 SLO | 10 次故障取 P95 | P95 < 60s | 延迟统计 |
| 处置延迟 SLO | 10 次故障取 P95 | P95 < 300s | 延迟统计 |
| Trace 完整性 | 检查所有 trace entry | 100% 完整 | 审查报告 |
| LLM 成本 SLO | 5min 窗口成本统计 | < 预算上限 | 成本报告 |

## 最终验收: 性能验证全链路

| 维度 | 内容 |
|------|------|
| 测试方法 | 完成 P0-P2 全部 checkpoint，产出成本模型 + 压测报告 + SLO 基线 |
| 通过标准 | LLM 成本模型偏差 < 10%；3 并发故障全部处置完成；1 小时运行无资源泄漏；4 项 SLO 全部达标 |
| 验收证据 | 成本预估表 + 压测 trace 全量快照 + 资源消耗趋势图 + SLO 验收报告 |

## 成功标准 (Exit Criteria)

- LLM 调用成本模型建立，单次链路成本预估偏差 < 10%
- 5min / 1h / 24h / 7d 四级成本预估表产出，区分去重/未去重场景
- LLM 调用预算上限和熔断阈值定义，与 ProactiveBudget 集成无旁路
- 单故障端到端延迟 < 60s，多故障并发不崩溃
- RFC-006 信念去重效果验证：LLM 调用降低 > 80%
- 1 小时持续运行无资源泄漏（内存增长 < 20%，连接数稳定）
- 4 项 SLO 基线定义并达标：检测延迟、处置延迟、Trace 完整性、LLM 成本
